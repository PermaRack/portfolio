FEATURED PROJECT

Gaming today. Local AI next.

A Proxmox homelab project exploring how one GPU-backed environment can support Steam/Proton gaming and, eventually, local AI workloads.

Ongoing · Gaming foundation validated · AI planned
PLATFORM

Proxmox + Ubuntu LXC

An unprivileged Ubuntu container with 16 CPU cores, 48 GiB of memory, and a 120 GB system disk.

ACCELERATION

Intel Arc Pro B50

Host-managed GPU access for rendering, physical display output, and audio. Local AI acceleration is a future phase.

EXPERIENCE

Steam + Proton

A local desktop gaming experience supported by directly mounted game storage and dynamically discovered input devices.

THE PROBLEM

Make shared hardware useful and dependable.

I wanted a single compute environment that could prioritize gaming while I was using it and perform local AI work when those resources were idle. The design also needed to fit alongside existing homelab services and support ongoing maintenance.

The initial challenge was establishing a dependable gaming foundation: graphics, audio, game storage, and physical input all had to work together before introducing AI workloads.

MY CONTRIBUTION

Design, implementation, and troubleshooting.

01

Evaluate architectures

I tested a Bazzite-based virtual machine, rebuilt with Ubuntu, and investigated a host crash triggered by GPU passthrough. PCI BAR allocation failures helped guide the move to an LXC environment using the host GPU driver.

02

Integrate the gaming stack

I configured GPU and audio access, a physical desktop, Steam/Proton, and a local game-library bind mount. This reduced the network-filesystem complexity encountered in the earlier design.

03

Make input maintainable

I worked through device permissions, udev classification, and Steam Input. Dynamic input discovery replaced mappings tied to changing event numbers, and a refresh helper supports recovery after reconnects.

ARCHITECTURE

A host-managed GPU, a containerized workload.

Proxmox host

Owns hardware drivers and device discovery. Provides GPU, audio, and input interfaces to the gaming container.

Ubuntu gaming container

Runs the desktop, Steam, and Proton, with a directly mounted local game library. Steam Input uses virtual-controller support.

Planned AI layer

Local inference and orchestration will use the available compute resources after monitoring establishes a reliable baseline.

RESULTS SO FAR

A working gaming foundation.

  • Validated GPU rendering, physical display output, and audio inside the Ubuntu LXC.
  • Launched representative games with Steam/Proton and validated local game storage.
  • Validated wired and Bluetooth input workflows and Steam virtual-controller support.
  • Validated an 8BitDo Ultimate 2 controller in Steam after refreshing input metadata.
  • Created runbooks and helper workflows for adding input devices and recovering session input.

Project documentation records these milestones in September 2026. Controller endurance testing and recovery-workflow refinement remain ongoing.

LESSONS LEARNED

Diagnose the boundary, then simplify the design.

Use evidence to change direction

Driver logs and stability tests were more useful than assuming full VM passthrough was the best fit. Changing the architecture helped establish a usable baseline.

Separate discovery from access

A device appearing in the container did not guarantee that the desktop or Steam classified it correctly. Permissions, metadata, and application state each required validation.

Document repeatable operations

Stable device identification and written runbooks make future additions easier to diagnose and maintain than one-off event-node mappings.

NEXT PHASES

Measure first. Add AI with a baseline.

  1. Monitoring: capture host/container CPU, memory, storage, network, GPU utilization, and driver health.
  2. Local inference: select a compatible runtime and benchmark models, resource use, and response latency.
  3. Orchestration: integrate Hermes with local/cloud routing and an approval workflow for infrastructure changes.
  4. Resource arbitration: have AI workloads yield when games launch, queue deferred work, and recover after gaming ends.
  5. Optimization: evaluate NPU use, CPU tuning, and model sizing using measured results.

These are planned capabilities; automated gaming/AI handoff is not yet implemented.
